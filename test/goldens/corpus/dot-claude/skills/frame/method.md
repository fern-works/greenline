# Frame: the method

It runs where the change's mode reaches the frame step, at the depth the mode gives it, and alone when the owner asks for it by name: "grill me", "grill with docs", or a term doing two jobs, which it names in one line with the sharper word it proposes.

Asked for by name, or loaded by a start, with no change open, it runs at the written depth, its result stays in the reply or in a discussion's record, and it writes no other file. It reads the settled decisions first, in the repository's decision home and the change's record, and reopens none of them.

## The method

Name the intent, and find the one consequential question the request leaves open, if there is one. A term the request leaves unclear is such a question: put it to the owner, never settle it by your own reading. Ask it with your recommended answer and wait.

Think the request through thirteen nodes: purpose, scope, adjacent, journey, surface, data, behaviour, security, performance, operations, verification, constraints and generic. Every question names its node. Open only the nodes the request touches, and never ask for a node's sake; say in one line which you left closed, and why. Settle purpose and scope in the first round. At careful every node but generic is asked or closed with its reason, and the owner confirms the restatement before anything outside the change's homes is built, as [references/greenline.md](references/greenline.md) says.

At regular and careful, open the constraints node on one sentence: Reduce this problem to its irreducible constraints and rebuild it from zero. Name the limits the request cannot move, apart from the shape the code holds now, and write them in the frame section as its constraints.

Read the repository's documents before the first question: its decision home, its glossary (the repository's own, or `GLOSSARY.md` where it keeps none) and the records of earlier changes in the same area, so that no question asks what they already settle.

Read the code the request touches before the first round, and name its files in the frame: a question the code answers is not asked. Read the `situation:` and `owes:` lines the status line prints, and do what they say: load each skill the `owes:` line names before the step that uses it.

Where the situation line names a floor on a public contract or a security boundary, or the code the request touches stands on one, offer the `invariants` start in one sentence before the proposal: its list names what the code relies on there and the door that would hold it, and each entry it marks is a floor the proposal names.

Where the frame interviews the owner, run the interview in [references/interview.md](references/interview.md) to its end: every behaviour the request leaves open goes to the owner, each with your recommended answer, and none is settled on your own.

## When asking cannot settle a question

Two kinds of question are answered by work rather than by asking, and each has its page, read only when one arises:

- A question that waits on a fact the repository does not hold: look it up yourself, the web included, and name its source; at careful, a question that needs a reading of its own is proposed as research, as [references/research.md](references/research.md) says.
- A question only trying can answer, whether a logic or state model feels right or what a screen should look like, or a design with no precedent whose shape is not chosen yet: [references/prototype.md](references/prototype.md).
