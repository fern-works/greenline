# Build: the practice's mechanics

This page holds build at each mode's depth and where its work lands: the section, the checks it runs, the commits it makes and the files it writes on the way. Read it with `SKILL.md` when the mode reaches build, and when AGENTS.md's index sends you here.

## The depths

- **Inline, at quick.** Build the change by `SKILL.md`'s slices, and write the change record's build section, in `.greenline/ledger/<id>.md`, as one line: what was built and the check that shows it, with any deviation from the plan.
- **Written, at regular and careful.** Build the change by `SKILL.md`'s slices, and write the build section: what was built, slice by slice; each deviation from the plan, with what you decided and why; each approach tried and dropped, with what dropped it; and what was noticed outside the task and left alone. At careful the build starts only once anticipate's report is in and the plan answers its findings: a premise review run after the code is no premise review.

## While it runs

While a long build runs, say in one line per act what you learned or decided, in the owner's words, such as "Red for the right reason: the search finds nothing for a lower-case name. Now the fix." Never say which page, skill or tool you are loading, a retry or an editor's quirk, and never paste a table. A slice that moves a shape, a module extracted or a schema, a state machine or a flow changed, shows the resulting shape inline on the turn it lands, in one of show-me's six forms: prose alone does not show a shape.

## Checks

Every run of the change's code goes through `greenline check`, its red runs, a baseline, a probe and an assertion script included, the builder's and every fresh agent's alike; a probe, a run whose green the change never claims, is then marked with `greenline check --change <id> --probe <fact>`, which keeps it out of the change's checks, as the verify skill says. A recorded check fact is never removed or edited: a rerun records a new one. Every file written on the way and not part of the change, a probe, a scratch script or a before-and-after copy, yours or a fresh agent's, goes under `.greenline/tmp/<id>/`, never the host's temporary directory, and a check's facts cite paths inside the repository. That folder is this change's own, under its own id: a test or a script that needs a scratch folder takes it from the open change, never from a path an earlier change left in the code, and a path naming another change's folder is moved before the commit.

Run each of `SKILL.md`'s increment checks, and the completion contract's final test run, through `greenline check -- <command>`, its red runs included, so the change's checks record it: the short form takes the open change and the step its record is in, and names that step beside the facts, so give `--change <id> --step <step>` where it names another. A run of the change's code you make only to read, a failing test's detail or a quick look after an edit, is a check too: `greenline check -- node --test --test-name-pattern=<name> <file>` records it, and its output shows as it runs, so read the detail there. Each such command is a check of its own: once its cause is fixed, run it again green, since `done` waits on the latest run of every check. A probe, a baseline at an earlier commit, a mutation run or a negative control, is recorded the same way and marked a probe: no run you cite stays plain. `greenline status --change <id>` counts the commits since the last recorded check, and a count above zero is code committed since that no recorded check saw.

## The file token cap

Where the manifest's `fileTokens` is set, every authored file the change writes stays under its cap, 5,000 tokens unless it names another, a token counted as four bytes. `greenline check files` reads the files named, else the staged ones, else those the working tree changed or added, and refuses one over the cap with its count and how to split it; lockfiles, generated files, vendored trees, data and the manifest's `fileTokens.exempt` globs are left out. Run it through `greenline check -- greenline check files --max-tokens <cap>` before each slice's commit, so a red run is a fact of the change that `done` waits on. A file that grows past the cap is split in a slice of its own, the move committed before any other change to either part. It is a declared check, never a git hook, and where `fileTokens` is absent no cap applies.

## Commits

Where the request names the mode and no proposal waits for the owner's yes, the first reply still states, in one line before the first edit, the record's included, the mode, the ground, the branch or the worktree as `greenline status` names it, and any repository rule you read that bears on it, such as a contribution guide's rule on branches; a rule named only after the commits is named too late.

Each slice's commit goes on the change's branch, the one its proposal named or, for a ticket, the planning change's, never another change's, in the form [commits.md](commits.md) gives, and the change's first commit carries its record, `.greenline/ledger/<id>.md`, since `greenline status` reads history only from the commit where the first change record entered. A change commits once for each slice that leaves its checks green, once as its record first enters and at every stop, which commits the record and its folder alone. Stage the slice's files by name, `git add <path>...`, never `git add -A`, `git add .` or `git commit -a`, so a file the owner or another change left in the tree stays out of the slice's commit. Stage the record and its folder by path too, `git add .greenline/ledger/<id>.md .greenline/ledger/<id>/`, never the ledger folder whole: git's pre-commit hook refuses a commit that stages another change's record or folder, such as a finished change's visuals file the inspector rewrote, naming the path; unstage it and tell the owner it changed. A commit carries one change's trailer: on a planning change's branch a ticket's commit carries the ticket's own, never two tickets'. Every commit's subject, a stop's and the close's included, takes the form [commits.md](commits.md) gives, `<type>(<scope>): <imperative summary>`, never a bare sentence, unless the repository keeps a convention of its own.

Every commit carries the trailer `Greenline-Change: <id>` from the moment it is made, as the last line of the message's last paragraph, one block with any trailer the harness adds there, such as `Co-Authored-By`; `Greenline-Agent: <harness>/<model>`, the record's `agent` line, stands just above it, and the git hooks write both where the message lacks them and the record states the agent; no commit, an unpushed one included, is reset, amended, rebuilt or rewritten with `filter-branch` to move it. A trailer-shaped line of another key, such as `Related-Change: <id>`, put in a message after a hook refuses it is not an answer to the refusal: report the refusal to the owner and ask. Generated code follows its generator; vendored contributions follow their upstream's contract.

A slice that breaks is fixed forward from the last commit. Throwing its work away is the owner's word, written in the record's `discard` line: the harness hook refuses `git reset --hard`, `git clean -f`, `git checkout .` and `git restore .` until that line holds it, `git branch -D` until it or the `landing` line does, `git push --force` until the `rebase` and `landing` lines both do, and a push to a branch other than the change's until the `landing` line does, each refusal naming the line that lifts it. A line lifts only once the record is committed with it: quote the owner's words into it, commit the record alone, then run the act, since an uncommitted line goes with the work a reset throws away. A request that leads to the act, such as "start over", is not those words: they lift it only when they say so of that act. A project's own pre-commit tooling runs beside greenline's hooks, never in their place. A hook's refusal is answered by the line it names, never by `--no-verify`, which is the owner's bypass alone. A refusal you believe wrong is reported to the owner by its first sentence, in their terms, and never worked around, by a working copy set apart from the index or any other way.

## The processes you start

A server or a watcher you start in the background, with `&`, `nohup` or the harness's own background run, is noted for the session by the hooks, and `greenline status` names those still running as `running:`. Stop a process by its pid, one the session started: the harness hook refuses `pkill`, `killall`, `fuser -k` and a `kill` with no literal pid, since a pattern reaches the owner's own processes too, and refuses a `kill` of a pid the session did not start until the owner's words name that pid, which you quote in the record. To free a port the owner's process holds, ask the owner, naming the pid and what it runs. The close stops what the session started.

## Secrets and guidance

Protect secrets and keep guidance bodies in tool output, never in a local library or task compilation; a key or a variable that may hold one is checked for presence, never printed, even while diagnosing.

## An interface change

On a change whose record says `interface: yes`, read design's craft page before the first write to an interface file, and the pages its facets name. The harness hook returns the interface rules' findings after each such write: fix a floor finding before you go on. A reflex finding you keep, on the owner's yes, is waived by a line in the build section, `waived: <rule>: <reason>; the owner's yes: "<the owner's words>"`; a standing waiver in the `## Interface` rulings of `.greenline/DECISIONS.md` covers the whole workspace. A floor finding is never waived by you or by a standing waiver: fix it, or put it to the owner on a card, and their answer goes in the record's `## Interface` section, as design's references say.
