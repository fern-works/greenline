# Frame: the practice's mechanics

This page holds the frame step at each mode's depth and where its work lands, with what comes before it: the orientation, reading the situation, a question, the proposal, where the commits go and the record's opening. Read it with `SKILL.md` when the mode reaches frame, and when AGENTS.md's index sends you here.

## The depths

- **Inline, at quick.** Run `SKILL.md`'s method for the intent and the one open question. The change record's frame section, in `.greenline/ledger/<id>.md`, is that one line: the intent, then the open question with its answer, or a start's answers, or none. The line credits the owner only with a choice the owner made, in the request or in an answer; a choice you made is written as yours. It also names each floor found and where it came from, and under a mode the owner chose below one, the floor's reason.
- **Written, at regular.** Read the repository's documents first, as `SKILL.md` says, and write the frame without an interview round with the owner: the section restates the ask, states the acceptance, names every floor found with where it came from, and lists the open questions the request leaves, each answered from the repository and the request with the answer taken, so the owner can correct it on the proposal.
- **Written, at careful, and when frame is asked for by name.** Read the repository's documents, then run the interview in [interview.md](interview.md) to its end. At this depth every behaviour the request leaves open goes to the owner through the interview, each with your recommended answer, and none is settled on your own. A question to the owner goes in the reply that ends your turn, and you wait there for the answer; never put it through a side channel the owner may not see, such as a harness's asynchronous user-input call. A behaviour the scope the owner accepted already settles is yours: decide it within that scope and name it in the frame section and the reply as your choice; one it leaves open still goes to the owner. The frame section holds the confirmed restatement with its out-of-scope list, the terms the interview settled, the floors found with where each came from, and any question the owner chose to leave open.

## Where research and prototypes land

A fresh agent that does the research page's reading gets the one brief every fresh agent gets (`.greenline/ledger/README.md`, "The brief and the relay note"), and its report is `.greenline/ledger/<id>/<step>-<n>.md`, named for the step the reading serves. The change's folder is `.greenline/ledger/<id>/`, its working files `.greenline/tmp/<id>/`, and a plan directory, whose research and prototypes the plan step writes, `.greenline/plans/<NNN-name>/`. A prototype, a probe and every other scratch file of the change go in its own working files, `.greenline/tmp/<id>/` under the id of its record, never in a folder under another id.

## The orientation

With no change record on any branch, local or remote-tracking, the first request for a change is the orientation: on an empty tree (commits `none`, languages `none found`) it is `groundwork`, its own change before a feature request or the request's own when it asks for setup; otherwise a survey, `architecture-survey` where installed or a read of the top-level documents, its result written into the knowledge homes `.greenline/WORK.md` names under a quick record opened first. Load a start only at the orientation, when the request begins in its row's situation in AGENTS.md, or when the owner names it: it runs until it hands the job to a mode.

## Reading the situation

Find the intent, the current work, the authority and the affected roots in the repository's evidence: the request, the open and stopped change records under `.greenline/ledger/`, the repository's own instructions (its contributing or law file and the instructions outside the managed markers of AGENTS.md) and its decision home. Before your first proposal in a session, read the situation line `greenline status` prints. Read the decisions book, `.greenline/DECISIONS.md`, when it exists. A path's nesting neither inherits nor overrules a decision; sibling roots stay independent. Lost context requires rereading the material the work needs, not crediting a compaction summary as a full read.

## Questions and named steps

A question needs no mode and no record, and neither does a step asked for by name that changes no file ("review this branch", "verify this", "grill me"), or a start that edits no file. A decision or a term written only into the knowledge homes (the decisions book, the ADR home, the glossary) opens a quick record first, as every write does. A factual question about this repository is answered from its files, as AGENTS.md's loop says. A follow-up inside an open change joins that change.

## The proposal

Before any edit, state the mode you would use from the table in AGENTS.md, the reason, its cost in agents and rounds, any floor or risk you found, and whether this session can start a second agent: it can when the harness exposes a delegation tool in this session, and you never start one to find out. Then state where the commits go, below, and wait. The owner accepts it or names another mode or branch, and that choice is final; a mode named above yours has its cost in agents and rounds restated before the work. A request that names a mode or a branch has chosen it. Proceed without waiting in two cases only: the request names the mode, or the workspace's `proceed` setting allows the proposed mode (none by default). The owner's yes to a mode is the record's choice line, `owner` or `accepted`, written after the proposal: a request to commit, to checkpoint, to "go ahead" or to put a fix straight into a file is not that yes, and neither are words saying to implement without asking. A `choice: standing` applies only where `proceed` admits the mode, that mode and every faster one; elsewhere the hooks refuse it. The proposal still comes before the first edit, the mode stated as taken with its reason and the where line, and asks only a substantive choice the request leaves open. The proposal, and any question with it, goes in the reply that ends your turn, never through a side channel the owner may not see.

Raising the mode during the work is a new proposal and waits the same way. Under a mode the owner named, a floor or a risk found later is reported and changes nothing; under a proposal the owner accepted, propose the raise it calls for. Either way the record names every floor found, as the ledger guide says. While the tree holds another change's uncommitted edits, propose no new change: say so and wait for the owner, whatever `proceed` or the request allows. A change's id is chosen at its proposal, or earlier for a start's working file.

## Where the commits go

The where line names the branch the change's commits will go to, read from local facts only, the current branch, the default branch, the remotes, a pull-request template and a CI workflow, with no network command: read the remote's state only as the repository holds it, its remote list, `refs/remotes/<remote>/HEAD` and the remote-tracking branches beside it, and the current branch's upstream, and before the proposal never run `git ls-remote`, `git fetch`, `git pull` or any other command that contacts a remote. It is the current branch when that is not the default branch or the repository has no remote, and otherwise a new branch, `greenline/<id>`. On a detached HEAD, name no branch and ask. The default branch is `origin/HEAD`, else `init.defaultBranch`, else the branch HEAD names unless it is a change's branch, as the ledger guide defines one, and with none, name no branch and ask; on another change's branch, never that branch: the default branch where there is no remote, and otherwise one made from it, `greenline/<id>`. A repository rule pulling the other way, in a contribution guide or a branch policy, is named beside the branch the local facts give, never in its place. In a repository with no remote, the git hooks hold the change whose record is open on the current branch, the default one included, as on a branch of its own: its trailer on every commit, no commit before its `choice` line. Where no change is open on the branch HEAD names, as on the default branch of a repository with a remote, which is never a change's branch, the hooks hold the workspace: they refuse a commit there, a local landing's close aside, and a write outside `.greenline/ledger/` and `.greenline/tmp/`.

Where a repository rule forbids committing on the branch the local facts give and the request names no branch, ask which, recommending `greenline/<id>`, and start once it is answered; a branch the owner leaves to you is one the repository's rules allow, never one they forbid. A worktree holds the change's checkout only on the owner's request and only where the harness runs the session in it; you never make one.

## Opening the record

Before the first edit, switch to the branch the proposal named, creating it when it is new, and write `.greenline/ledger/<id>.md` from the skeleton for its mode in `.greenline/ledger/README.md`, which says when it is `open` or `stopped`. Every mode keeps the whole record: a step the mode does not run holds the one line `none at <mode>`, written as the record opens. One session writes the record at a time, the one holding the change. The change's first commit carries its record: `greenline status` reads history only from the commit where the first change record entered.

## Authority

Instructions and standing grants, explicit repository choices and actual platform constraints govern. Conventions are evidence; a consultation informs a justified gap and settles nothing the repository decided. Source prestige grants no authority. Surface a real conflict with its evidence rather than averaging opposing advice, and continue independent authorized work when a conflict blocks only another part. Maintain authority permits scoped upkeep of established choices; observe authority leaves proposed changes for the owner. Choose roots explicitly; the CLI does not infer which scope governs. The owner names the work; you maintain the practice's installed files only as that work and its grant warrant.
